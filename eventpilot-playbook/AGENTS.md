# AGENTS.md — EventPilot Playbook

## 1. 專案目的

EventPilot Playbook 是一個「校園活動企劃知識卡網站」，提供活動總召可以快速查閱的實務指南。

這個專案的重點不是只做出目前這幾個頁面，而是建立一套**可以被 AI 重複遵循的內容與開發規則**。任何 AI 在修改本專案前，都應先閱讀本檔案，再依照下列規則新增內容或修改網站。

網站語言固定為 **繁體中文（zh-TW）**。

## 2. 使用技術

- HTML5
- CSS3
- Vanilla JavaScript
- 不使用建置工具
- 不使用 Node.js
- 不使用前端框架
- 不依賴外部 API
- 所有路徑使用相對路徑

除非使用者明確要求，AI 不得自行加入 React、Vue、Tailwind、Bootstrap 或其他新框架。

## 3. 專案結構

```text
eventpilot-playbook/
├── AGENTS.md
├── README.md
├── index.html
├── guide.html
├── styles.css
├── app.js
└── data/
    └── guides.js
```

### 各檔案責任

- `AGENTS.md`：AI 開發與內容規則。
- `README.md`：給人閱讀的專案簡介與使用方式。
- `index.html`：首頁，只負責網站框架、搜尋、分類與指南卡片容器。
- `guide.html`：所有指南共用的詳細頁。
- `styles.css`：全站共用視覺樣式。
- `app.js`：渲染首頁卡片、搜尋分類與指南詳細內容。
- `data/guides.js`：內容唯一來源（single source of truth）。

## 4. 核心開發原則

1. 一般新增指南時，不建立新的 HTML。
2. 只在 `data/guides.js` 的 `window.EVENTPILOT_GUIDES` 陣列新增一筆資料。
3. 首頁會自動產生卡片。
4. 詳細頁統一使用 `guide.html?id=<guide-id>`。
5. 不為單一內容重寫 `app.js` 或 `styles.css`。
6. 不修改與需求無關的檔案。

## 5. 視覺規則

- 清爽、溫和、有校園活動企劃感。
- 主色：`#6D5CE7`
- 輔助藍：`#4E9BE8`
- 淺紫背景：`#F5F3FF`
- 頁面背景：`#FAFAFC`
- 文字：`#25243A`
- 次要文字：`#6B6A7C`
- 卡片使用圓角、柔和陰影與充足留白。
- 手機版必須可閱讀，不可產生橫向捲動。

## 6. 指南資料格式

每篇指南必須符合以下結構：

```js
{
  id: "rain-plan",
  title: "雨天備案怎麼準備？",
  emoji: "☔",
  category: "風險管理",
  summary: "一句話說明這篇指南能幫使用者解決什麼問題。",
  level: "入門",
  updatedAt: "2026-11-10",
  intro: "2～4 句前言。",
  steps: [
    { title: "步驟名稱", description: "具體可執行的說明。" }
  ],
  checklist: ["可以直接勾選或檢查的項目"],
  tips: ["額外提醒或容易忽略的細節"]
}
```

## 7. 命名規則

### guide id
- 使用英文小寫 kebab-case。
- 不使用空白。
- 不使用中文檔名作為 id。
- id 一旦發布後不要任意更改。

正確：`rain-plan`、`staff-roles`、`event-countdown`

錯誤：`RainPlan`、`雨備`、`staff_roles`、`page01`

### 檔案名稱
- HTML / JS / CSS 檔名使用英文小寫。
- 多字使用 kebab-case。
- 不建立 `final-final-v2.html` 這類版本式檔名。

## 8. 新增內容的規則

當使用者要求「新增一篇指南」時，AI 應：

1. 先閱讀本 `AGENTS.md`。
2. 確認新主題是否已存在。
3. 決定唯一且語意清楚的英文 `id`。
4. 在 `data/guides.js` 新增一筆物件。
5. 使用現有 category；只有真的無法分類時才新增分類。
6. steps 建議 3～6 個。
7. checklist 建議 4～8 個。
8. tips 建議 2～5 個。
9. 文字使用繁體中文、台灣常用詞彙。
10. 不建立新的 HTML 詳細頁。
11. 確認首頁搜尋與分類可以找到這篇指南。
12. 確認 `guide.html?id=<id>` 可以正常顯示。

## 9. 內容寫作規則

- 像有活動經驗的學長姐整理實用筆記。
- 直接、具體、可執行。
- 不寫空泛的「加強溝通」「注意安全」而不說怎麼做。
- 避免長篇學術式說明。
- 不用過度可愛或大量 emoji。

如果內容涉及校方規定、場地規範、保險、消防、法規、價格或特定單位政策，而專案中沒有可靠來源：
- 不得自行捏造。
- 請寫成「請向場地方／主辦單位確認」。
- 不要把推測寫成確定事實。

## 10. 分類規則

目前優先使用：
- 前期規劃
- 時程管理
- 人力分工
- 現場執行
- 風險管理
- 活動收尾

## 11. UI 修改規則

1. 優先沿用既有 CSS class。
2. 新增樣式前先確認是否能以既有元件組合完成。
3. 不要移除搜尋、分類篩選、返回首頁等既有核心功能。
4. 不得破壞手機版。
5. 不要把內容硬編碼到 `index.html`。
6. 內容仍應來自 `data/guides.js`。

## 12. JavaScript 規則

- 使用原生 JavaScript。
- DOM 找不到時要安全處理。
- 使用 `textContent` 處理一般文字。
- 不使用 eval。
- 不引入不必要的第三方套件。

## 13. 無障礙與可用性

- 所有按鈕或連結有可理解文字。
- 搜尋框有 label 或 aria-label。
- 鍵盤 focus 狀態可見。
- 色彩不是唯一的資訊提示方式。
- 標題層級合理。
- 手機寬度約 375px 時仍可正常閱讀。

## 14. 完成修改前 QA Checklist

- [ ] 首頁可以開啟。
- [ ] 指南卡片正常產生。
- [ ] 搜尋功能正常。
- [ ] 分類篩選正常。
- [ ] 每張卡片連結到正確的 `guide.html?id=...`。
- [ ] 不存在重複 guide id。
- [ ] 詳細頁能顯示標題、步驟、Checklist 與提醒。
- [ ] 不存在指南時有友善錯誤畫面。
- [ ] 桌面與手機版都沒有明顯跑版。
- [ ] 沒有修改與需求無關的檔案。

## 15. AI 完成任務時的回覆方式

完成後，AI 應簡短說明：
1. 修改了哪些檔案。
2. 新增了什麼內容或功能。
3. 是否需要使用者確認任何真實世界資訊。
4. 如何自行測試。

## 16. 未來擴充範例

使用者可以直接說：

> 請依照 AGENTS.md，新增一篇「活動遇到下雨怎麼辦？」的指南。

AI 應知道：
- 不建立新的詳細頁 HTML。
- 在 `data/guides.js` 增加一筆資料。
- category 使用「風險管理」。
- id 可使用 `rain-plan`。
- 依照既有資料欄位補齊 steps、checklist、tips。
- 完成後檢查首頁與詳細頁網址。

## 17. 規則優先順序

1. 使用者當下明確要求
2. 本 `AGENTS.md`
3. 現有程式與視覺慣例
4. AI 自行判斷
